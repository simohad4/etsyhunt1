# M4.7 offline durable-dispatch protocol model

This is a pure, bounded TypeScript model, not a worker, database lock, RPC client or transport. Every state/result is deeply frozen and explicitly synthetic/unverified. activationBlocked=true, executionAuthorized=false, automaticRetryAllowed=false, requiresAuthoritativeDatabaseValidation=true. durableTransitionApplied, authoritativeResolutionVerified and invoiceFinalityVerified remain false. There is no mayDispatch/sendAuthorized flag. A fresh modeled transition is not a capability to send anything. The API still returns 503 and active prices/caps remain unchanged.

## API, identities and persistence simulation

`createResearchDispatchProtocol(identity)` accepts exactly requestId/attemptId/provider/providerIdentifier/intentDigest. IDs use a bounded local grammar; provider identity uses existing pins; the digest is 64 lowercase hex characters. The caller supplies the digest: no binding to actual bytes is cryptographically established. It should eventually cover owner, full request, prompt/schema/routing/build and pricing context. State does not establish authenticated ownership. Immutable scope is repeated on every command; mismatched request/attempt/provider/digest rejects.

`transitionResearchDispatchProtocol(state,event)` returns assessment transitioned/replay/rejected, stable reasonCode and holdReasonCodes, and state (null if the snapshot is invalid). Commands have unique eventId and immutable scope; exact replay returns **current** state without rewinding it or granting a second action. Changed replay rejects. Inputs are exact-key inert data, not hostile JavaScript proxies. Accessors and callbacks are rejected. A bounded history (128 commands) is reconstructed and compared with the supplied snapshot, preventing accidental summary tampering. This is consistency checking, not authentication: callers can construct another self-consistent synthetic history. Billing ledger limit is 64 unique events. Rejections preserve the validated original state, with fixed errors and no raw error text. Creation rejects malformed identity with a fixed typed error.

## Transitions

| Command | Required conditions | Model effect |
| --- | --- | --- |
| claim | expectedEpoch matches; no submission boundary; no unexpired claim | claimed, one owner, epoch +1 |
| arm | current worker/epoch; claimed; supplied time before lease expiry | submission_armed; permanently crosses submission boundary and latches uncertainty |
| uncertain | same owner/epoch; crossed boundary; not reconciled | acceptance_unknown without external ID, otherwise reconciliation_hold |
| bind_provider | crossed boundary; no final execution outcome; first ID or identical binding | provider_accepted, or retains reconciliation_hold after uncertainty |
| outcome | same owner/epoch; accepted; exact external ID | provider_completed/provider_failed; uncertainty remains until reconciliation |
| reconcile | exact scope/external ID, current history revision, no prior reconciliation; authority/freshness/quiescence claims; consistent decision | records one execution decision; retains any pending financial hold; never invoice finality, dispatch or retry |
| billing | unique/identical event binding and bounded safe amounts | append only; late adjustments create reconciliation_hold and pending financial reconciliation |

`unclaimed` is the initial state. Outcome states and `reconciled` are advisory labels only. A provider failure does not imply zero or known billing. No path resets submissionBoundaryCrossed: even a not_submitted reconciliation cannot reopen the same attempt for sending. The caller would need a separately designed and explicitly authorized future process; no retry mechanism exists here.

Times are supplied synthetic safe integers, not a trusted clock. Exactly expired pre-arm claims can be reassigned, increasing epoch; paused old workers then fail fencing. Expired post-arm claims can never be reassigned for submission. Lost arm replies, timeouts, disconnects, partial results, post-send crashes and unknown acceptance remain latched. Identical arm replay is descriptive only. A sender can be paused before an external send: database fencing alone cannot stop that HTTP operation. Quiescence and negative evidence must be independently established before a real not-submitted decision. Provider idempotency is never assumed.

The first reconciliation requires expectedRevision equal to the current history length. After it is recorded, every new reconciliation command rejects with RECONCILIATION_CONFLICT, even with a new evidence ID and the same decision. Exact event replay returns current state safely; changed content under the original event ID rejects with CONFLICTING_REPLAY. Replaying an old reconciliation after a late charge never clears the financial hold. Corrections require a separate future authoritative, permission-checked and audited procedure; this model provides no correction operation. Caller authoritative/fresh/priorSenderQuiesced flags are explicitly unverified synthetic claims. An advisory resolution never transitions M2, refunds credits, settles budgets or grants retries.

Historical executionOutcome is separate from financialReconciliationStatus. The latter starts unverified and becomes pending on any late adjustment, including a credit or explicit zero adjustment. No operation marks financial reconciliation settled. A late adjustment preserves the recorded execution outcome and does not reopen execution uncertainty. Even a first execution reconciliation received after an adjustment retains the financial hold. FINANCIAL_RECONCILIATION_PENDING makes this explicit in result hold reasons; invoiceFinalityVerified and finalCostsVerified remain false.

## Synthetic billing model

Billing commands contain billingEvent `{id,kind,amountMicroUsd,inputTokens,outputTokens}` and inherit the original scope. Kinds distinguish estimate, reported_usage, billing_event, invoice and late_adjustment. One estimate, one usage snapshot and one invoice snapshot per attempt are supported; additional snapshots reject rather than double counting cumulative totals. Billed events and signed late adjustments are additive, keyed by unique event IDs. Same ID/same content deduplicates; changed replay rejects. Non-estimate records require a crossed submission boundary. Numeric cost fields and token counts are safe bounded integers; only adjustments may be negative. All token fields must be null except on reported_usage.

The single reported-usage and invoice limits are deliberate offline simplifications: the model has no verified contract identifying cumulative versus incremental usage, invoice coverage or overlapping periods. Real providers may emit multiple partial usage events or multiple invoices. Those cases are unsupported here, not evidence of invalid provider behavior. A future separately reviewed ingestion contract must establish event scope, aggregation, deduplication and correction semantics before accepting them; this document does not invent a live billing schema. Missing evidence remains unknown, never zero.

Unknown amounts remain null. No entries in a category means unknown, not zero. Explicit zero is retained. If any event in a category has unknown amount, its subtotal stays unknown. Aggregate sums use BigInt and reject positive/negative safe-integer overflow. Billed-plus-adjustment cost is unknown unless both categories are explicit; no adjustment entries are not proof of zero adjustments. Invoices are evidence snapshots, not extra charges added to billed totals. No document or amount is authenticated, reconciled against a provider account or considered final. This model does not invent listing counts, starts, demand charges, rates or token usage. A future billing ingestion layer must distinguish requested/returned/billed listings and individual billable event categories.

## Proposed future SQL and RPC contract — not implemented

Minimum durable structures: (1) per-attempt dispatch row with owner, immutable request digest, epoch, lease and irreversible submission boundary, (2) append-only submission/reconciliation evidence and audit events, (3) append-only uniquely identified billing events/adjustments bound to original request, attempt, provider and accounting period. External ID is first-write/matching replay only. Protect evidence retention independently of Auth deletion. Preserve original M2 job/attempt statuses instead of replacing them with dispatch states.

Proposed backend-only operations: claim/renew pre-boundary ownership; arm immutable submission intent; bind accepted external identity; hold uncertain outcomes; reconcile a held attempt with authoritative evidence; record billing evidence and apply audited financial adjustments. Every operation needs a unique operation ID, expected row version/epoch, immutable argument binding, server-verified actor/worker authority and exact replay semantics. Lost responses must never yield a second send capability. Existing begin admission remains necessary but insufficient; legacy entry points must not bypass new invariants.

Use SECURITY DEFINER with pinned owner/search_path and schema-qualified objects. Revoke PUBLIC/anon/authenticated and direct table writes, expose narrowly scoped service-role-only operations, enable RLS, and validate persisted owner/request/attempt/provider relationships. A claimed workerId or actorId is not authentication. Reconciliation authority requires a separately designed permission/audit contract; existing research.view is insufficient and M1.5 audit actions do not yet represent research reconciliation.

Proposed lock ordering: serialize each request first, then job, attempt and dispatch records; when financial scopes are touched, lock global then account liability guards, global then account windows, then the reservation and credit/account records according to one reviewed cross-RPC order. Review all existing lifecycle functions together before adopting an order—do not mix incompatible orders with old RPCs. Keep network operations outside transactions. Financial adjustments, holds and audit events must commit atomically and deduplicate billing evidence. Missing billing must not release liability as zero. Finished M2 outcomes are immutable; late adjustments need a separate operation, not weakened replay checks.

**Existing M2 hardening prerequisite:** `finish_research_provider_attempt` checks external-ID equality for finished-outcome replay, but its first finish of a started attempt assigns `COALESCE(p_provider_attempt_id,provider_attempt_id)`. A supplied different non-null ID can replace a previously stored ID on that path. A future separately reviewed migration must enforce first-write/matching identity there and provide early acceptance binding. This task does not modify or execute SQL.

Before migrations or live integration: review schemas/RPC authorization and all bypass paths, establish authoritative actor build/full raw schema and provider routing/completion contracts, verify billing and sufficient reserves, resolve the existing cost-cap mismatch without simply raising caps, update staging parity expectations only through a reviewed process, and separately authorize staging concurrency/rollback tests. No paid call is covered by transactional rollback. Current offline success does not establish deployed parity, actual leases or exactly-once provider execution.
